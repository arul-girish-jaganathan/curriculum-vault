# 11: Calling Conventions

## Definition
A calling convention is the standardized low-level implementation contract governing how functions exchange data and control flow at the machine instruction level. It dictates which CPU registers hold arguments, how return values are transferred, which registers are preserved across calls (callee-saved) versus scratched (caller-saved), and how the stack frame is organized and dismantled.

## Scope and Boundaries
*   **Covers:** Target ABIs (AAPCS for ARM, System V AMD64, RISC-V ABI), register parameter mappings, caller-saved vs. callee-saved registers, stack alignment rules, and explicit convention attributes.
*   **Does not cover:** High-level parameter passing semantics (see [[03_Parameter_passing]]), return value semantics (see [[07_Returning_values]]), or stack allocation mechanics in isolation.

## Why Does It Exist
Compilers, linkers, and hand-written assembly routines must interoperate seamlessly:
*   **Binary Interoperability:** Allowing object code generated by different compilers (e.g., GCC, Clang, IAR) or written in assembly to link and execute correctly.
*   **Register Maximization:** Defining common agreements on register usage to minimize slow stack access.
*   **OS/RTOS Integration:** Providing predictable register preservation contracts for context switches and interrupt handling.

## Mechanism and Language Rules
1.  **Architecture Application Binary Interface (ABI):** The calling convention is defined by the processor architecture ABI, not by ISO C.
2.  **Register Classes:**
    *   *Argument / Scratch (Caller-Saved):* Registers used for passing parameters and temporary math. If the caller needs their values preserved across a call, the caller must push them to the stack.
    *   *Preserved (Callee-Saved):* Registers the callee is required to restore before returning. If the callee modifies them, it must push them in the prologue and pop them in the epilogue.
3.  **The Stack Alignment Rule:** Modern ABIs mandate strict stack pointer alignment upon function entry (e.g., 8-byte alignment on ARM AAPCS, 16-byte alignment on x86_64).
4.  **Hardware Floating Point (Hard-Float vs. Soft-Float):**
    *   *Soft-Float:* Float/double parameters are passed in general-purpose integer registers.
    *   *Hard-Float:* Floats are passed directly in dedicated FPU registers (`S0-S15`, `D0-D7`).

## Examples

```c
/* Keep examples minimal: prove the rule before embedding it in a larger API. */
#include <stdint.h>

/* ARM Cortex-M AAPCS Demonstration:
 * a -> R0 (Argument / Scratch)
 * b -> R1 (Argument / Scratch)
 * c -> R2 (Argument / Scratch)
 * d -> R3 (Argument / Scratch)
 * Returns sum in R0
 */
static int32_t aapcs_demo(int32_t a, int32_t b, int32_t c, int32_t d)
{
    return a + b + c + d;
}

/* Explicit compiler calling convention attributes (x86 systems) */
#if defined(__i386__)
__attribute__((cdecl)) void legacy_call(int a);
__attribute__((stdcall)) void win32_api_call(int a);
#endif
```

## Undefined, Unspecified, and Implementation-Defined Behavior
*   **Undefined Behavior:** Calling a function through a function pointer with an incompatible calling convention. Violating the ABI stack alignment requirements prior to executing a function call.
*   **Implementation-Defined:** Default compiler calling convention settings and architecture-specific calling attributes (`__cdecl`, `__fastcall`, `__stdcall`).

## Edge Cases and Failure Modes
*   **Stack Misalignment Faults:** On ARM Cortex-M or x86_64, calling functions (or floating-point SIMD operations) with an unaligned stack pointer (`SP % 8 != 0`) will trigger hardware faults (e.g., `UsageFault` or general protection faults).
*   **Soft-Float / Hard-Float Toolchain Mismatches:** Linking a library compiled with `-mfloat-abi=softfp` against an application compiled with `-mfloat-abi=hard` results in corrupted floating-point parameters, as caller and callee look in completely different hardware registers.

## Embedded Implications
*   **ARM AAPCS Register Map:**
    *   `R0-R3`: Parameters and return values (Caller-saved).
    *   `R4-R11`: Local variables (Callee-saved).
    *   `R12 (IP)`: Intra-procedure scratch register.
    *   `R13 (SP)`: Stack Pointer (8-byte aligned at external boundaries).
    *   `R14 (LR)`: Link Register (holds return address).
    *   `R15 (PC)`: Program Counter.
*   **RTOS Context Switches:** When an RTOS context switch occurs, the kernel must save all registers according to the ABI. On Cortex-M, the hardware automatically pushes `R0-R3, R12, LR, PC, xPSR` on exception entry; the RTOS software stack saves the remaining callee-saved registers (`R4-R11`).

## Firmware Review Angle
1.  **Assembly Interfaces:** Ensure hand-written assembly routines strictly preserve callee-saved registers (`R4-R11` on ARM) before returning to C callers.
2.  **Stack Alignment in ASM:** Verify that manual assembly stack allocations adjust `SP` by multiples of 8 bytes.
3.  **Toolchain ABI Flags:** Ensure all compiled static libraries and application code share identical ABI build flags (e.g., `-mabi=aapcs`, `-mfloat-abi=hard`).

## Compiler, ABI, and Toolchain Implications
*   **Prologue/Epilogue Optimization:** Compilers optimize prologues to push only the specific callee-saved registers modified by the function body.
*   **Vector Calling Conventions:** Compilers utilize vector extensions (e.g., ARM Helium, AVX) to pass array chunks across registers when supported by the ABI.

## Performance, Memory, Timing, and Power
*   **Register-Bound Throughput:** Keeping function parameters <= 4 ensures zero memory load/store instructions are needed for parameter transfer.
*   **Prologue Cycle Overhead:** Touching many callee-saved registers increases prologue/epilogue instruction count, adding cycle latency to short functions.

## Verification / Debugging
*   **Compiler Diagnostics:** Compile with `-Wcast-function-type` to detect calling convention and signature mismatches on function pointers.
*   **GDB Register Tracing:** Step into assembly instructions (`stepi`) and check register states (`info registers`) to verify argument mapping.

## Safety, Security, and Reliability
*   **MISRA C:2012 Compliance:**
    *   *Rule 1.3:* There shall be no occurrence of undefined behavior (strictly bans calling convention violations).
*   **Security Vulnerabilities:** Calling convention mismatches corrupt stack frames, allowing attackers to hijack return addresses stored on the stack.

## Trade-offs and Alternatives
*   **Standard ABI vs. Specialized Attributes:** Use standard ABI conventions across all C interfaces. Reserve custom attributes (`__attribute__((interrupt))`) strictly for hardware-bound vector entry points.

## Staff-Level Takeaway
Calling conventions are the bridge between C's abstract machine and physical silicon. A Staff engineer must ensure strict ABI homogeneity across all third-party libraries and build scripts, audit assembly code to ensure rigorous callee-register preservation, and enforce 8-byte stack alignment to prevent hardware faults.
