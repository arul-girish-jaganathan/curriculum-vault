# signal model

> Canonical C topic note — chapter 34.

## Definition
A C **signal** is an asynchronous notification delivered to a process to report an event such as an exceptional condition, termination request, or implementation-defined external event. ISO C exposes a small signal facility through `<signal.h>`: `signal()`, `raise()`, `SIG_DFL`, `SIG_IGN`, and a set of implementation-defined signal macros.

Signals are not interrupts in the ISO C sense. The standard specifies a portable process-level notification model; the operating system, C library, ABI, and target decide how signals are represented and delivered. Hosted implementations normally provide more signal behavior than freestanding embedded implementations.

## Mechanism and language rules
`signal()` installs a handler for a specified signal number or restores default/ignore handling. A signal may be generated by `raise()` or by an implementation-specific mechanism. Delivery transfers control to the registered handler asynchronously with respect to the interrupted execution.

The important model is:

1. Normal program execution is in progress.
2. A signal becomes pending or is otherwise generated according to the implementation.
3. The implementation arranges for the signal handler to execute.
4. The handler returns, or performs another permitted control transfer.
5. Normal execution resumes or the implementation terminates the program according to the signal and handler semantics.

A signal is **not** a C exception and does not provide a general-purpose transaction/rollback mechanism. Handler invocation can occur between ordinary C evaluations, so code must not assume a convenient source-level boundary.

### What to reason about
- Signal identifiers are macros with implementation-defined values; never assume numeric values.
- `signal()` has a handler type involving an `int` signal number and returns a handler-designator value.
- Some signals cannot be caught or ignored, depending on the implementation.
- Signal delivery and ordering are implementation-dependent beyond the guarantees of the C standard.
- A signal handler may interrupt code while library state, locks, buffers, or invariants are temporarily inconsistent.
- A signal is not equivalent to a thread, interrupt, callback, or C++ exception.
- The C standard's signal model is narrower than POSIX's richer `sigaction`, signal masks, alternate stacks, and real-time signals.

## Embedded implications
Many MCUs do not provide an operating-system signal facility at all. A bare-metal compiler may provide `signal()` only as a stub, omit it in a freestanding environment, or implement a vendor-specific mechanism.

On an embedded target, confusing signals with hardware interrupts is dangerous. An ISR is entered through processor/vector-table machinery and has target-specific priority, masking, register, stack, and latency rules. A C signal handler is part of a hosted runtime abstraction.

If signals exist through an RTOS or embedded libc, document the exact implementation contract. Treat signal delivery latency, stack usage, nesting, masking, and available handler operations as target properties rather than ISO C guarantees.

### Firmware review angle
For a signal-based design, verify:
- whether the selected libc actually implements signals;
- whether the application is hosted or freestanding;
- which signals exist and how they are generated;
- whether the handler executes on the normal task stack or a special stack;
- whether libraries used from the handler are safe;
- what happens during reset, boot, low-power states, and fault handling.

## Edge cases and failure modes
Common hazards include:
- assuming every POSIX signal exists in ISO C;
- assuming a signal is delivered immediately;
- doing complex work inside a handler;
- modifying ordinary shared objects from a handler without respecting signal rules;
- assuming signal arrival occurs at a source-code statement boundary;
- relying on signal numbers being portable;
- treating `signal()` as a reliable inter-thread synchronization primitive;
- forgetting that default signal actions can terminate execution.

A particularly misleading intuition is that a handler behaves like an ordinary function call. It does not: it can interrupt an execution context whose invariants are not visible from the handler source.

## Example pattern
```c
#include <signal.h>

static volatile sig_atomic_t stop_requested;

static void on_signal(int signo)
{
    (void)signo;
    stop_requested = 1;
}

int main(void)
{
    if (signal(SIGINT, on_signal) == SIG_ERR) {
        return 1;
    }

    while (!stop_requested) {
        /* Perform bounded application work. */
    }
    return 0;
}
```

The example deliberately communicates a request rather than performing substantial work in the handler.

## Verification / debugging
Test signal behavior under normal execution, while blocked in library calls, during shutdown, and at different optimization levels. On POSIX-like systems, compare the actual implementation with ISO C assumptions; on embedded targets, inspect the libc/RTOS documentation and generated startup/runtime code.

Staff-level questions:
- Is a signal genuinely required, or is an explicit event/message mechanism clearer?
- What is the exact implementation contract?
- What state can be interrupted while the handler runs?
- What happens if the signal arrives repeatedly?
- What happens if it arrives during shutdown or fault handling?

## Staff-level takeaway
Treat ISO C signals as a constrained asynchronous notification facility, not as a general exception system. The architecture should minimize handler work and make all implementation-specific behavior explicit.
