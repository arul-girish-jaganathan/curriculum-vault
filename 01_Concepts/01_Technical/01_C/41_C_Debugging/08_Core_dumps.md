# Core dumps

> Canonical C topic note — Chapter 41. A core dump is a snapshot of process/runtime state captured after a failure; the format and capture mechanism are platform-specific, while the C language does not define core dumps.

## Definition
A core dump normally records memory and register/context information sufficient to analyze a crashed process offline. On hosted systems this may be generated by the operating system. Bare-metal firmware usually needs an explicit crash-record design because there is no general-purpose OS core-dump facility.

## Mechanism and language rules
Useful state includes the faulting PC, stack pointer, registers, fault/status codes, active task identity, stack contents, and selected memory regions. Symbolic analysis maps addresses back to source using the exact executable and debug information.

### What to reason about
- Is the captured PC the faulting instruction or a return/handler address?
- Is the stack pointer valid enough to unwind?
- Does the dump correspond to the exact binary version?
- Which memory regions are trustworthy after corruption?
- Could collecting the dump itself overwrite evidence?
- Are sensitive secrets present in captured RAM?

A dump is a snapshot, not a complete execution history. It can establish state at failure but usually cannot prove the entire causal timeline without logs, trace, counters, or persistent breadcrumbs.

## Embedded implications
For MCUs, a practical crash dump often stores a compact header, reset reason, fault status, PC/LR/SP, general registers, task/ISR context, stack bytes around the failure, and a small event history into retention RAM, battery-backed RAM, or reserved flash. Flash writes must account for endurance and power loss.

Crash capture must be bounded. A fault handler that attempts to format strings, allocate memory, use a locked peripheral, or perform complex filesystem I/O can fail recursively and destroy the original evidence.

### Firmware review angle
Define a versioned dump schema and include firmware build ID, image hash, CPU/core identifier, reset reason, and validity marker. Use CRC or another integrity mechanism when persistence is important. Avoid storing unrestricted RAM if security policy prohibits secrets from surviving reset.

## Edge cases and failure modes
- **Corrupt stack:** normal backtrace may be impossible; rely on saved exception context.
- **Double fault:** the crash handler itself can fault.
- **Power loss:** flash write can be torn.
- **Wrong symbols:** addresses resolve to misleading source locations.
- **Overly large dump:** capture latency and storage requirements become unacceptable.

## Example pattern
```c
struct crash_record {
    uint32_t magic;
    uint32_t version;
    uintptr_t pc;
    uintptr_t sp;
    uint32_t fault_status;
    uint32_t crc;
};
```
The record is a format contract. `uintptr_t` is useful for storing an address representation, but the meaning of the captured PC/SP remains target-specific.

## Verification / debugging
Intentionally trigger controlled faults in a test image and verify that the handler captures the expected context, survives reset, validates integrity, and can be decoded offline. Test interrupted writes, repeated crashes, full storage, corrupted records, and incompatible schema versions.

Staff-level questions:
- What minimum state is required to localize the fault?
- How is the exact binary identified?
- What happens if the fault handler faults again?
- What is the storage wear and security model?

## Staff-level takeaway
Design a crash dump as a **diagnostic protocol**, not an ad-hoc memory dump. Keep capture bounded and robust, preserve the machine context that matters, version the format, and pair snapshots with timeline evidence when root cause requires more than state-at-failure.
